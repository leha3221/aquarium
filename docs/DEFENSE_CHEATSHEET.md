# Шпаргалка к защите

## Почему многослойная архитектура?
UI отвечает за консоль, Service — за бизнес-правила, Repository — за SQL/JDBC. Поэтому код не смешивается.

## Где ООП?
- Инкапсуляция: поля моделей `private`, доступ через методы.
- Конструкторы и методы: `Client`, `ServiceRequest`.
- Enum: `RequestStatus`, `AquariumType`, `ServiceType`.
- Интерфейс: `Exporter`.
- Полиморфизм: переменная типа `Exporter` может содержать `ExcelExporter` или `CsvExporter`.
- Коллекции: `List<ServiceRequest>`.
- Stream API: поиск, фильтрация, сортировка.

## Почему PreparedStatement?
Параметры передаются отдельно от SQL. Это безопаснее конкатенации строк и позволяет использовать параметризованные запросы.

## JDBC
`Connection` — соединение; `PreparedStatement` — параметризованный SQL; `ResultSet` — результаты SELECT; try-with-resources автоматически закрывает ресурсы.

## 5+ бизнес-правил
1. Клиент должен существовать.
2. ФИО, телефон и адрес обязательны.
3. Email должен быть корректным.
4. Приоритет только 1–5.
5. Стоимость не может быть отрицательной.
6. Описание заявки обязательно.
7. Нельзя удалять заявку со статусом IN_PROGRESS.
8. Переходы статусов ограничены.

## Поиск
- по описанию;
- по имени клиента.

## Фильтры
- по статусу;
- по минимальному приоритету.

## Сортировки
- по плановой дате;
- по стоимости.

## Статистика
Количество клиентов, заявок, статусов, высокоприоритетных заявок и сумма завершённых услуг.

## Связь БД
`clients.id` — PRIMARY KEY.
`service_requests.client_id` — FOREIGN KEY на `clients.id`.


## Новые сущности
Aquarium хранит владельца, название, тип и объём. Fish хранит аквариум, вид и
количество рыб. У обеих сущностей собственные Model, Repository, Service и меню.
Внешние ключи образуют цепочку clients → aquariums → fish с каскадным удалением.
Поиск: название аквариума и вид рыбы. Фильтры: клиент, тип, аквариум.
Сортировки: объём аквариума и количество рыб. Статистика дополнена новыми сущностями.
Миграция sql/migration_aquariums_fish.sql добавляет таблицы без удаления старых данных.
